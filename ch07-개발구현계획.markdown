## 7.1 개발 환경 및 기술 스택

### 구성

| 구분 | 기술 | 선정 이유 |
|---|---|---|
| **모바일 앱** | Flutter | 영상 촬영·업로드가 휴대폰에서 일어난다. 단일 코드로 iOS·Android를 함께 대응한다 |
| **웹** | Next.js | 카드·스쿼드 **공개 공유 페이지**와 팀·운영 화면을 담당한다 |
| **API 서버** | FastAPI (Python) | 분석 라이브러리가 Python 생태계에 있어 언어를 분리하지 않아도 된다 |
| **영상 분석** | 자세 추정 라이브러리 (CPU 실행) | 별도 GPU 서버 없이 처리한다. 6.3에서 확정한다 |
| **데이터베이스** | **AWS RDS** PostgreSQL + **pgvector** | 지표·이력 저장과 특징 벡터 유사도 검색을 한 곳에서 처리한다. 관리형 서비스로 두어 운영 부담을 줄인다 |
| **AI 에이전트** | Claude API | 요청 해석, 특징 요약, 추천 사유 생성 |
| **실행 환경** | Docker · **AWS** | 분석 워커와 API 서버를 분리해 배포한다. 계정은 IAM 사용자로만 운용하고 루트 계정은 사용하지 않는다 |

### 앱과 웹의 역할 분담

클라이언트를 둘로 두되 **같은 기능을 두 번 만들지 않는다.** 각각이 담당하는 영역을
분리한다.

| | 담당 | 근거 |
|---|---|---|
| **앱** (Flutter) | 영상 촬영·업로드, 분석 리포트, 선수 카드, 매칭 지원·수락, 상호 평가 | 촬영과 알림이 필요한 개인 사용 흐름 |
| **웹** (Next.js) | **카드·스쿼드 공개 페이지**, 팀 관리, 구인 공고 관리, 운영자 도구 | 링크로 열리는 공유 화면과 큰 화면이 필요한 작업 |

웹의 공개 페이지가 필수인 이유는 **확산 경로 때문**이다(3.5). 카드를 공유했을 때
앱 설치 없이 링크만으로 열려야 유입이 발생한다. 앱 안에만 카드가 있으면 공유 자체가
성립하지 않는다.

### 개발 부하에 대한 판단

인원 4명·기간 10주에 클라이언트가 둘이면 부하가 크다. 따라서 웹의 범위를 다음과 같이
제한한다.

- 웹은 **공개 페이지(카드·스쿼드)를 필수 범위**로 하고, 팀 관리·운영자 도구는 조정
  가능 범위로 둔다.
- 웹 착수는 앱과 분석 흐름이 연결된 **스프린트 3부터** 시작한다.
- 앱과 웹은 **동일한 API를 사용**한다. 화면만 다르게 구현하고 서버 로직을 이중화하지
  않는다.

## 7.3 조직 구성 및 역할 분담

### 역할

개발은 **애자일 스크럼** 방식으로 수행한다. 인원이 4명이므로 스크럼 마스터를 별도로
두지 않고 PM이 겸한다.

| 이름 | 역할 | 담당 범위 |
|---|---|---|
| **백성검** | PM · 클라이언트 개발 | 일정·백로그 관리, 스프린트 운영, **Flutter 앱** 개발 |
| **박민호** | 영상 분석 파이프라인 | 전처리, 자세 추정, 지표 산출, 분석 워커 |
| **정상호** | AI 에이전트 | 요청 해석, 특징 요약, RAG 기반 검증·추천 |
| **정어진** | 백엔드 · 데이터 · **웹** | API, 데이터베이스, 벡터 검색, 인증·스토리지, Next.js 웹 |

> 확인 필요 — 정어진의 담당 범위는 잠정안이다. 팀 협의 후 확정한다.
> 웹까지 맡기면 부하가 크므로, 스프린트 4 이후 웹 공개 페이지 구현에 백성검이 일부
> 참여하는 방안을 함께 검토한다.

### 역할 간 연결

각자의 산출물이 다음 사람의 입력이 되는 구조다. **경계에서 주고받는 형식을 스프린트 1에
먼저 고정**하고, 이후에는 각자 병렬로 진행한다.

```
박민호 ─ 분석 지표(JSON) ─→ 정어진 ─ API·벡터 검색 ─→ 정상호 ─ 추천·요약 ─┐
   영상 → 자세 지표            저장 · 조회             적합도 판단        │
                                  │                                      ▼
                                  └──→ 웹(공개 페이지)          백성검 ─ 앱 화면
```

인터페이스 규격이 늦게 정해지면 세 사람이 동시에 대기하게 되므로, 이 항목을 스프린트 1의
최우선 과제로 둔다.

## 7.4 단계별 개발 일정

### 진행 방식

| 항목 | 내용 |
|---|---|
| 방법론 | 애자일 스크럼 + 칸반 보드 |
| 스프린트 | **2주 단위, 총 5회** ({{ site.report.period_start }} ~ {{ site.report.period_end }}) |
| 데일리 스크럼 | 매일 15분. 어제 한 일 · 오늘 할 일 · 막힌 것 |
| 스프린트 계획 | 스프린트 첫날. 백로그에서 이번 스프린트 항목을 선정한다 |
| 스프린트 리뷰 | 스프린트 마지막 날. **동작하는 결과물로 시연**한다 |
| 회고 | 리뷰 직후. 다음 스프린트에 적용할 개선 1~2가지를 정한다 |

문서가 아니라 **동작하는 결과물로 진척을 확인한다.** 스프린트마다 시연 가능한 산출물을
남기는 것을 원칙으로 한다.

### 칸반 보드

작업은 아래 6열 칸반 보드에서 관리한다. **진행 중(WIP) 한도**를 두어 여러 작업을 동시에
벌여 놓는 것을 막는다.

| 열 | 정의 | WIP 한도 |
|---|---|---|
| **Backlog** | 전체 요구사항. 우선순위 순으로 정렬한다 | — |
| **Sprint Backlog** | 이번 스프린트에서 하기로 한 항목 | — |
| **In Progress** | 실제 작업 중 | **1인당 2** |
| **Review** | 코드 리뷰·상호 확인 대기 | **전체 4** |
| **Blocked** | 외부 요인·의존성으로 멈춘 항목. 데일리에서 매일 확인한다 | — |
| **Done** | 완료 정의(DoD)를 충족한 항목 | — |

카드는 **담당자 · 스프린트 · 관련 기능 코드(F-01 등)** 를 함께 표기해 3장 기능 정의와
연결한다.

#### 스프린트 3 시점 보드 예시

| Sprint Backlog | In Progress | Review | Blocked | Done |
|---|---|---|---|---|
| F-05 후보 추천 API *(정어진)* | F-02 지표 산출 고도화 *(박민호)* | F-03 분석 리포트 화면 *(백성검)* | F-04 적합도 가중치 *(정상호)* | F-01 영상 업로드 |
| F-13 호칭 부여 규칙 *(정상호)* | F-13 카드 화면 *(백성검)* | | ↳ 지표 표본 부족으로 대기 | F-01a 규격 사전 검사 |
| F-09 상호 평가 *(백성검)* | | | | F-02 자세 추정 연동 |

### 완료 정의 (Definition of Done)

아래를 모두 충족해야 Done으로 옮긴다.

1. 기능이 로컬 환경에서 **실제로 동작한다.**
2. 다른 팀원 1명 이상이 코드를 확인했다.
3. 인터페이스 변경이 있으면 규격 문서를 갱신했다.
4. 예외 상황(잘못된 입력, 실패 응답) 처리가 있다.
